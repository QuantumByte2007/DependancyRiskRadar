1. Résumé Exécutif

Cette session avait pour objectif d'analyser, corriger et opérationnaliser le pipeline CI/CD du projet Dependency Risk Radar, une application web d'analyse de risques de dépendances Android. Le pipeline couvrait l'analyse statique du code (SAST), la détection de secrets, l'audit des dépendances (SCA) et le scan des images Docker.

3. Structure du Pipeline CI/CD

Deux workflows GitHub Actions ont été définis : CI (Ci.yml) dédié à la sécurité et qualité du code, et CD (Deploy.yml) pour le déploiement en production. Suite à l'audit de cette session, le pipeline CI a été simplifié pour ne conserver que les étapes d'analyse sécurité.

4. Anomalies CI/CD Détectées & Corrigées

L'audit initial du pipeline a révélé 7 anomalies critiques empêchant l'exécution correcte des workflows. Toutes ont été corrigées avant le premier push.
🔴 Anomalie 1 — Mauvais chemins dans tous les jobs CI/CD
Problème : Tous les jobs référençaient backend/ et frontend/ à la racine du dépôt. Le code applicatif se trouve dans dependency-risk-radar/backend/ et dependency-risk-radar/frontend/.

Correction : Mise à jour de toutes les occurrences dans Ci.yml et Deploy.yml (8 occurrences) : working-directory, context, cache-dependency-path, pip install -r, pip-audit -r, bandit -r.
🔴 Anomalie 2 — Nom de fichier Docker Compose avec espace
Problème : Le fichier s'appelait "docker compose.prod.yml" (espace) mais le workflow référençait docker-compose.prod.yml (tiret).

Correction : Renommage du fichier via git mv.
🔴 Anomalie 3 — Endpoint de health check inexistant
Problème : Le smoke test du déploiement appelait GET /api/v1/health mais le backend n'exposait que GET /health.

Correction : Ajout du second décorateur @app.get("/api/v1/health") sur la fonction health() dans app/api/main.py.
🔴 Anomalie 4 — ESLint absent du frontend
Problème : Le job sast-js exécutait npx eslint src/ mais ESLint n'était pas dans les devDependencies et aucun fichier .eslintrc.json n'existait.

Correction : Ajout de eslint, eslint-plugin-react, eslint-plugin-react-hooks dans package.json et création du fichier .eslintrc.json avec configuration React/JSX.
🟡 Anomalie 5 — npm ci sans package-lock.json
Problème : Le workflow utilisait npm ci (qui requiert un lock file) mais package-lock.json était absent. Changement temporaire vers npm install.

Résolution : Le fichier package-lock.json existait finalement dans le dépôt — retour à npm ci avec cache keyed sur ce fichier.
🟡 Anomalie 6 — .env.prod.example manquant
Problème : Le workflow CD copiait .env.prod.example vers le serveur via SCP mais ce fichier n'existait pas.

Correction : Création du fichier avec les variables d'environnement requises (DATABASE_URL, GEMINI_API_KEY, DOCKERHUB_USERNAME).
🟡 Anomalie 7 — Bandit --exit-zero : SAST ne bloquait jamais
Problème : La commande Bandit incluait --exit-zero, ce qui forçait un code de sortie 0 même en cas de vulnérabilités trouvées. Le job SAST ne bloquait donc jamais.

Correction : Suppression du flag --exit-zero.

6. Améliorations Structurelles

6.1 Séparation des dépendances de test

Les dépendances de test (pytest, pytest-asyncio, pytest-httpx) ont été déplacées dans un fichier dédié requirements-test.txt. Cette séparation suit les bonnes pratiques :

  • L'image Docker de production n'installe que requirements.txt
  • L'audit de sécurité (pip-audit) ne scanne que les dépendances de production
  • Les conflits de versions entre outils de test et packages de production sont évités

6.2 Simplification du pipeline CI

Conformément à la demande, les étapes de build Docker (build-and-test) et de scan d'images (container-scan via Trivy) ont été temporairement retirées du workflow CI. Le pipeline se concentre désormais uniquement sur les 5 étapes d'analyse sécurité, réduisant le temps d'exécution de ~8 minutes à moins de 30 secondes.
